* Emacs 30 strict plist checking

In Emacs < 30, ~plist-put~ on a non-plist (like a string) silently
created a new plist and discarded the original value — it "worked" by
accident. Emacs 30 added strict type checking for plist operations, so
passing a string now signals ~wrong-type-argument plistp~. Any
third-party code that relied on this leniency will break on upgrade.

When patching =.el= files managed by package managers like el-get,
always delete the corresponding =.elc= — Emacs loads bytecode
preferentially, so a stale =.elc= silently ignores your source fix.

* Unicode smart quotes in Emacs Lisp

The character =' (U+2018, LEFT SINGLE QUOTATION MARK) looks like a
quote but is a multi-byte Unicode character. Emacs Lisp reads it as a
symbol name, not as the ~quote~ special form.  This means ~'foo~
produces the symbol ~'foo~ (with the curly quote as part of the name)
rather than ~(quote foo)~.

Common source: pasting code from web pages, PDFs, or rich-text editors
that auto-convert ASCII quotes to typographic quotes.

* Portable home directory paths

Emacs resolves =~= to the user's home directory via ~expand-file-name~
internally. This works on macOS (=/Users/scs=), Linux (=/home/scs=),
and Windows (=C:/Users/scs=). Using =~/= instead of hardcoded absolute
paths makes configs portable across machines and usernames.

For paths consumed by external programs (like ~inferior-lisp-program~),
wrapping with ~expand-file-name~ ensures =~= is resolved to an absolute
path immediately, which is safer for subprocess invocation.

* no-littering for data file paths

Rather than defining custom helper functions (like ~user-data~) for
locating data files, use ~no-littering-expand-var-file-name~ (for
variable/state data) and ~no-littering-expand-etc-file-name~ (for
configuration data). These place files under =var/= and =etc/=
subdirectories respectively, keeping the Emacs directory clean.

* Consolidating package managers for a single package

When a package is loaded by both ~package.el~ (via ~:ensure~) and
~el-get~ (via ~el-get-bundle~), Emacs warns about the conflict at
startup. The fix is to choose one manager per package. For packages
like ~org-contrib~ that provide multiple features (~ob-ly~,
~org-expiry~, etc.), a ~use-package~ block with ~:config~ that
requires the sub-features is cleaner than scattered ~require~ calls,
because it centralizes the dependency and makes the load order explicit.

Avoid ~:ensure pkg~ on a /different/ package's ~use-package~ block
(e.g., ~:ensure org-contrib~ inside ~(use-package org ...)~) — this
installs the package but doesn't configure it. Give it its own block.

* RCS keyword expansion

RCS expands keywords on check-in (~ci~). The keyword pattern
(dollar-sign + name + dollar-sign) must be present in the working file
before the first check-in. Once expanded, RCS recognizes and
re-expands it on subsequent check-ins automatically.

*Caution:* RCS expands /every/ matching keyword pattern in the file,
including ones in documentation text. Avoid writing literal keyword
patterns in body text — they will be expanded and mangled on check-in.

Useful keywords (by name):
- *Id* — filename, revision, date, author, state, locker
- *Log* — accumulates commit messages (can bloat files)
- *Date*, *Author*, *Revision* — individual fields

Emacs VC mode (~C-x v v~) auto-detects RCS and handles check-in/out.

* early-init.el save-and-restore pattern

Setting ~file-name-handler-alist~ or ~vc-handled-backends~ to ~nil~
during startup is a common optimization, but you /must/ save the
original value beforehand and restore it in ~emacs-startup-hook~.
Failing to restore ~file-name-handler-alist~ breaks TRAMP (remote file
access), compressed file reading (=.gz=, =.bz2=), and any filename
"magic" (e.g., =jka-compr=). Failing to restore ~vc-handled-backends~
disables all version control detection permanently.

The safe pattern is:

#+begin_example
(defvar my--saved-fha file-name-handler-alist)
(setq file-name-handler-alist nil)
(add-hook 'emacs-startup-hook
          (lambda () (setq file-name-handler-alist my--saved-fha)))
#+end_example

* Why move UI settings to early-init.el

Emacs evaluates ~early-init.el~ /before/ creating the initial frame.
Settings like ~(tool-bar-mode -1)~ placed in ~init.el~ cause the
toolbar to first appear (frame creation) then disappear (init.el
loads), producing a visible flicker. In ~early-init.el~, the mode is
disabled before the frame exists, so the toolbar never draws at all.

Similarly, ~package-initialize~ in ~early-init.el~ means packages are
available immediately when ~init.el~ starts, eliminating the need for
~package-enable-at-startup~ juggling.

* Cross-platform predicates: system-type vs window-system vs display-graphic-p

Three predicates serve different cross-platform purposes:

- ~system-type~ — identifies the OS kernel: ~'darwin~ (macOS), ~'gnu/linux~,
  ~'berkeley-unix~ (FreeBSD), etc. Use for OS-specific variables like
  ~mac-command-modifier~ that exist only in macOS Emacs builds.

- ~window-system~ — identifies the display backend for the /current frame/:
  ~'ns~ (macOS GUI), ~'x~ (X11), ~'w32~ (Windows), ~nil~ (terminal).
  Use for frame-parameter settings specific to a display system, e.g.
  ~undecorated-round~ is NS-only.

- ~(display-graphic-p)~ — returns non-nil when the current frame is a GUI
  frame (any backend), ~nil~ in terminal (~emacs -nw~) and ~--batch~ modes.
  Use for features that require a graphical display (toolbar, pixel
  scrolling, frame naming).

Rule of thumb: start with ~display-graphic-p~ (broadest GUI check), narrow
to ~window-system~ for display-backend specifics, use ~system-type~ for
OS-level concerns independent of display.

* executable-find for optional external tools

Wrapping configuration for external programs in ~(executable-find "prog")~
makes the config portable: settings are silently skipped on systems where
the tool isn't installed, avoiding "Searching for program: No such file or
directory" errors. This is especially useful for tools like ~aspell~,
~ugrep~, and ~rg~ that may not be present on all platforms.

* use-package :custom evaluates at expansion time

The ~:custom~ keyword in ~use-package~ calls ~customize-set-variable~
at *macro expansion time* — the value expression is evaluated
immediately when init.el is byte-compiled or loaded, NOT when the
package is lazily triggered via ~:commands~ or ~:defer~.

This means function calls in ~:custom~ values must reference code
that is *already loaded*:

#+begin_example
;; WRONG — no-littering may not be loaded yet when eshell :custom runs
(use-package eshell
  :commands eshell
  :custom
  (eshell-directory-name (no-littering-expand-var-file-name "eshell/")))

;; RIGHT — locate-user-emacs-file is always available (built-in)
(use-package eshell
  :commands eshell
  :custom
  (eshell-directory-name (locate-user-emacs-file "var/eshell/")))
#+end_example

Alternative: move the setting into ~:config~ (which runs after the
package loads and all prior init has completed).

* Quoted vs unquoted lambdas

Writing ~'(lambda ...)~ (with a quote) prevents byte-compilation and
makes the closure opaque to the compiler. In modern Emacs (24+),
~(lambda ...)~ is self-quoting — always use the unquoted form:

#+begin_example
;; WRONG
(define-key global-map (kbd "<S-f9>") '(lambda () (interactive) ...))

;; RIGHT
(define-key global-map (kbd "<S-f9>") (lambda () (interactive) ...))
#+end_example

* package-vc :rev :newest triggers network on every startup

When ~use-package~ specifies ~:vc (:url "..." :rev :newest)~, the
~:rev :newest~ (or the default ~:last-release~) tells ~package-vc~ to
check the remote repository for updates. This triggers
~package-refresh-contents~ (contacting 3 archive servers) and, if the
package is already installed, prompts "Overwrite previous checkout?"
— blocking startup entirely in daemon mode.

The fix is to guard with ~package-installed-p~:

#+begin_example
(unless (package-installed-p 'framemove)
  (package-vc-install '(framemove :url "https://...")))

(use-package framemove
  :init ...)
#+end_example

This way ~package-vc-install~ only runs on first install, not on
every startup.

* RCS lock workflow: rcs -l then ci -u

After ~ci -u~ (check in, unlock), the working file is read-only and
unlocked.  The safe cycle for subsequent edits is:

1. ~rcs -l file~ — lock the file *without* overwriting the working copy.
   This is critical: it preserves your local changes while acquiring
   the lock needed for check-in.
2. Edit the file.
3. ~ci -u -m"message" file~ — check in and immediately unlock, leaving
   the working file in place with updated RCS keywords.

*Why not ~co -l~?*  The ~co -l~ command checks out the /repository/
version and *overwrites* the working file.  If you have local edits
that haven't been checked in, they are silently destroyed.  Always
use ~rcs -l~ to lock an existing working file.

For batch check-ins (multiple files, same message):

#+begin_example
for f in init.el changes.org status.org; do
  rcs -l "$f" && ci -u -m"commit message" "$f"
done
#+end_example

* Dual Emacs server: sockets + TCP

Emacs supports multiple server instances by varying ~server-name~.
Using ~let~ to dynamically bind ~server-name~ and ~server-use-tcp~
around a second ~server-start~ call creates an independent server
without altering the global defaults.

Unix domain sockets (the default) work on all Unix-like platforms
(macOS, FreeBSD, SmartOS/illumos) and are what ~emacsclient~ looks
for automatically. TCP mode requires passing ~-f~ / ~--server-file~
to ~emacsclient~ with the path to an auth file.

Pattern:

#+begin_example
;; Default server: Unix socket (works with plain emacsclient)
(server-start)

;; Second server: TCP for apps that need it
(let ((server-name "scrim")
      (server-use-tcp t))
  (unless (server-running-p "scrim") (server-start)))
#+end_example

** TCP auth files vs Unix sockets

TCP mode creates a plain /auth file/ (containing IP, port, and auth
key) in ~server-auth-dir~.  Socket mode creates a Unix domain /socket
file/ in ~server-socket-dir~.  They look different on disk:

- Auth file: regular file (e.g. =server/scrim=), contains ~127.0.0.1:56242 70858 ...~
- Socket: socket file (=srwx------=) in the ~server-socket-dir~ tmpdir.

~no-littering~ redirects ~server-auth-dir~ but not ~server-socket-dir~,
so TCP auth files land under =var/server/auth/= while sockets still go
to the OS tmpdir (e.g. =/var/folders/.../emacs501/=).

** server-start and stale server files

~server-start~ will prompt interactively ("server file already exists;
delete it?") if it finds a leftover auth file or socket from a
previous session.  This blocks daemon startup.  If switching from TCP
to sockets (or vice versa), delete stale files before restarting, or
call ~(server-force-delete)~ first.

** emacsclient -a "" for daemon auto-start

Passing ~-a ""~ (empty string as alternate editor) tells ~emacsclient~
to start a new Emacs daemon if no server is found, then retry the
connection.  Combined with ~-n~ (no-wait), this is a reliable way to
ensure an Emacs server is always available from scripts or MCP tools:

#+begin_example
emacsclient -n -a "" -e '(emacs-version)'
#+end_example

*Caution:* the ~-a~ flag must be separated from its argument; combined
forms like ~-nwa ""~ cause argument parsing errors on some builds (the
parser reads ~""~ as the timeout for ~-a~ instead of the alternate
editor string).

* org-node for howm notes

~org-node~ provides fast, cache-based ID lookup across org files.
The ~(howm-create . org-node-nodeify-entry)~ hook automatically
adds an ~:ID:~ property to new howm notes, making them discoverable
via ~org-id~ and linkable with standard ~[[id:...]]~ links.

The ~(org-mode . howm-mode)~ hook enables howm's action-lock minor
mode in all org buffers, so comefrom links (~<<< keyword~) work
everywhere — not just in files opened through howm.

Populating ~org-id-extra-files~ with ~directory-files-recursively~
on the howm directory ensures that ~org-id-goto~ can jump to any
howm note by ID, even if it was never opened in the current session.

* Semantic howm filenames via after-save-hook

Howm's ~howm-file-name-format~ only supports ~strftime~ codes — it
cannot include the note title or tags because those don't exist when
the file is first created.  The workaround is an ~after-save-hook~
that renames the file once the content is known.

Key implementation details:

- Use ~set-visited-file-name~ with the third argument ~t~
  (~along-with-file~) to tell Emacs the file was already renamed on
  disk.  This avoids an infinite save loop since the rename happens
  inside ~after-save-hook~.
- Guard with ~file-in-directory-p~ to only rename files in the howm
  directory, not every org buffer.
- Check ~(not (file-exists-p new-path))~ before renaming to avoid
  clobbering an existing note with the same slug.
- Use ~y-or-n-p~ to let the user decline the rename, preserving the
  original filename when the title change was incidental.

This pattern is similar to ~denote~'s filename convention
(=DATE--TITLE__KEYWORDS.org=), adapted for howm with ~_~ as the
field separator.

* Stale MELPA archive cache and transitive dependencies

MELPA is a rolling-release archive — packages get new version
timestamps on every commit.  The local package archive cache (built
by ~package-refresh-contents~) stores download URLs with specific
version strings.  If a transitive dependency (e.g. ~el-job~, pulled
in by ~org-node~) gets a new release between cache refreshes, the
cached URL 404s with "Not found", even though the package still
exists on MELPA.

Fix: run ~package-refresh-contents~ (or ~M-x package-refresh-contents~)
to rebuild the cache, then retry the install.  For init.el resilience,
consider refreshing the cache on install failure:

#+begin_example
(unless (package-installed-p 'some-package)
  (condition-case nil
      (package-install 'some-package)
    (error
     (package-refresh-contents)
     (package-install 'some-package))))
#+end_example

This pattern avoids refreshing on every startup (slow) while
recovering gracefully from stale-cache errors.

* lexical-binding in init.el

Adding ~-*- lexical-binding: t -*-~ to the first line of =init.el=
enables lexical scoping. This is the modern Emacs default for new
files and is required by many packages. Without it, all variables use
dynamic binding, which can cause subtle bugs with closures and
~let~-bound variables in callbacks or hooks.

* Emacs Lisp case sensitivity

Emacs Lisp is case-sensitive for all symbol names. ~Set-input-method~
and ~set-input-method~ are completely different symbols. This is unlike
Common Lisp, which upcases symbol names by default via the reader.

When Emacs hits a ~void-function~ error during init, it aborts loading
the rest of the file. Everything after the error (packages, keybindings,
hooks) is silently skipped. Use ~emacs --debug-init~ to start Emacs with
the debugger enabled, showing exactly where and why init failed.

* RCS ci and file permissions

RCS ~ci~ (check-in) removes write permission by default. Using ~ci -u~
checks in and immediately checks out an unlocked (but readable) copy.
To keep the file writable afterward, run ~chmod u+w~ -- or use ~ci -l~
to keep the lock (file stays writable).

Emacs respects filesystem permissions: a file with mode 444 opens in
~read-only-mode~. The modeline shows ~%%~ instead of ~--~ to indicate
this. Use ~M-x revert-buffer~ after changing permissions externally.

* The Hyper modifier key as a free namespace

Most Emacs users run out of convenient keybindings because Control,
Meta, and Super are heavily used by Emacs and the OS. The Hyper
modifier (H-) provides an entirely free namespace of ~50+ keys that
never conflict with built-in Emacs bindings or OS shortcuts.

On macOS, mapping Caps Lock to Fn via Karabiner Elements, then setting
~ns-function-modifier~ to ~'hyper~, gives a comfortable Hyper key on
the home row. The bindings must be guarded with
~(when (eq system-type 'darwin) ...)~ since Hyper is not available on
other platforms without similar remapping.

A column-header comment above grouped ~global-set-key~ calls documents
the mnemonic for each binding at a glance, per the CLAUDE.md style for
repeated positional calls.

* corfu vs company

Company and corfu solve the same problem (in-buffer completion popup)
but use different architectures:

- *company* maintains its own backend/frontend system. You configure
  ~company-backends~ and ~company-frontends~ separately. This is
  powerful but adds complexity and can conflict with Emacs's native
  completion.

- *corfu* uses Emacs's native ~completion-at-point-functions~ (capf)
  infrastructure directly. The same capf functions that power
  ~completion-at-point~ (M-TAB) also drive corfu's popup. This means
  corfu works with any mode that provides capf support, and pairs
  naturally with ~orderless~ for fuzzy matching.

Cape (~completion-at-point-functions extensions~) adds additional capf
backends (dabbrev, file, history, etc.) that work with both company
and corfu. The ~cape~ configuration in init.el is preserved and works
with corfu unchanged.

* orderless completion style

The ~orderless~ completion style treats each space-separated word in
the input as an independent filter. "ob lan" matches
"org-babel-load-languages" because "ob" matches somewhere and "lan"
matches somewhere else, in any order. This is dramatically more
flexible than the default ~basic~ and ~partial-completion~ styles.

Setting ~(completion-styles '(orderless basic))~ means orderless is
tried first, with ~basic~ as fallback for completion frameworks that
don't support orderless (e.g. some TRAMP path completion).

* eshell prompt and eshell-prompt-regexp

The eshell prompt function and ~eshell-prompt-regexp~ must stay in
sync. Eshell uses the regexp to determine where the prompt ends and
user input begins -- it's how eshell knows which text is editable vs
which is the prompt. If the regexp doesn't match the actual prompt
string, eshell's command detection, C-a behavior, and input
highlighting all break.

When changing the prompt to include hostname, the regexp
~"^[^#$\n]* [#$] "~ matches "anything up to the # or $ delimiter",
which works for both ~hostname:path $~ and the old ~path $~ format.

* eat vs vterm for terminal emulation

Both ~eat~ and ~vterm~ provide full terminal emulation inside Emacs.
The key difference is build requirements:

- *vterm* requires ~libvterm~ (a C library) and compiles a dynamic
  module (~vterm-module.so~) on first use. This fails on systems
  without a C compiler or where the library isn't packaged (common
  on SmartOS, some FreeBSD jails).

- *eat* is pure Emacs Lisp with no C dependencies. It works on any
  platform that runs Emacs. Performance is slightly lower for
  high-throughput terminal output, but sufficient for interactive use.

The ~(eat-eshell-mode)~ hook makes eat handle eshell's "visual
commands" (like htop, vim, less) inside the eshell buffer itself,
instead of spawning a separate ~*ansi-term*~ buffer.

* diff-hl in terminal mode

~diff-hl~ uses the fringe (the narrow strip beside the line numbers)
to show VCS change markers in GUI Emacs. In terminal mode (emacs -nw),
fringes don't exist. The ~diff-hl-margin-mode~ fallback uses the
margin (the area beside the line numbers, rendered with text
characters) instead. The guard:

#+begin_example
(unless (display-graphic-p)
  (diff-hl-margin-mode))
#+end_example

ensures the right mode is activated based on the display type. diff-hl
works with any VC backend supported by ~vc~ (Git, SVN, RCS, Hg, etc.),
not just Git.

* tramp-histfile-override

By default, TRAMP runs a login shell on the remote host, which reads
~.bash_history~ / ~.sh_history~ and appends commands to it. This means
your remote shell history fills up with TRAMP's internal probe commands
(~test -e /bin/sh~, ~stty~ calls, etc.).

Setting ~tramp-histfile-override~ to ~t~ makes TRAMP set ~HISTFILE~ to
~/dev/null~ for its shell sessions, keeping remote history clean. The
user's normal SSH sessions still use the real history file.

* Emacs Lisp hex escapes vs Unicode escapes in strings

Emacs Lisp string escape sequences operate at the *character* level,
not the byte level. This distinction matters for non-ASCII characters:

- ~\xNN~ creates a character with code point NN (one character).
  ~"\xef\xbf\xbd"~ creates *three* characters with code points
  0xEF, 0xBF, and 0xBD respectively.

- ~\uNNNN~ creates one character with Unicode code point NNNN.
  ~"\uFFFD"~ creates *one* character: U+FFFD (the replacement character).

These are not the same:

#+begin_example
(length "\xef\xbf\xbd")  ;; -> 3  (three separate characters)
(length "\uFFFD")         ;; -> 1  (one Unicode character)
#+end_example

The confusion arises because in UTF-8 file encoding, the bytes
EF BF BD represent U+FFFD. But Emacs Lisp ~\x~ escapes produce
characters by code point, not UTF-8 byte sequences. To match a
Unicode character in a regex while keeping the source file ASCII,
use ~\uNNNN~:

#+begin_example
;; WRONG -- matches three separate characters, not U+FFFD
(string-match "\xef\xbf\xbd" str)

;; RIGHT -- matches the single U+FFFD character
(string-match "\uFFFD" str)
#+end_example
